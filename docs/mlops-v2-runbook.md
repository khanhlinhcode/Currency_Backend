# MLOps v2 staging operations

This runbook describes the additive MLOps registry and data approval workflow on the existing Render Free + Supabase staging deployment. It does not certify the legacy model for production.

## 1. Human review and dataset v2

The raw inventory has **10,106 images**, **367 exact-content duplicate groups** and **two originally conflicting-label groups covering four rows**. The dataset owner confirmed labels for those four rows on 2026-11-11; the local review queue now reports **zero pending label conflicts** but still lists **10,106 pending rows** because no physical-banknote/capture-session `group_id` has been attested. [Decision evidence](evidence/2026-11-11-label-conflict-resolution.json). The review CSV and source images are local and ignored by Git. The 182 groups crossing the old split are a separate audit finding.

```bash
python3 training/inventory_raw.py --raw dataset/raw --output results/raw-inventory-v2.json --review-csv results/group-review.csv
python3 training/review_queue.py --review-csv results/group-review.csv --queue results/review-queue.csv --report results/review-status.json
```

Re-running inventory preserves existing `reviewed_label`, `group_id`, `reviewed_by`, `reviewed_at` and notes when every source path and hash still matches. It stops if raw data changed. `--reset-review` explicitly discards prior decisions; do not use it during normal review. Open the pending queue, inspect the source images and provenance, then fill `results/group-review.csv`. Every raw row needs a physical-note or capture-session `group_id`, a reviewer ID and an ISO-8601 timestamp with timezone. For conflicting labels, fill `reviewed_label` on every duplicate copy. Exact hashes only establish byte equality and cannot establish physical-note identity.

For reviewers who do not edit CSV, use the [local browser review guide](data-review-ui.md). The loopback app updates the same CSV and status files without uploading raw data. After full human review, its one-click finalizer creates a versioned curation/split/audit snapshot. The app and finalizer were tested on fixtures; the real 10,106-image dataset remains unreviewed.

```bash
python3 training/review_queue.py --review-csv results/group-review.csv --queue results/review-queue.csv --report results/review-status.json --require-complete
python3 training/curate_raw.py --raw dataset/raw --review-csv results/group-review.csv --output dataset/curated_raw_v2 --group-template results/curated-groups-v2.csv --report results/curation-v2.json
python3 training/split_grouped.py --raw dataset/curated_raw_v2 --groups results/curated-groups-v2.csv --curation-report results/curation-v2.json --dataset-version 2.0.0 --output dataset/processed_v2 --attested-physical-groups
python3 training/audit_dataset.py --root dataset/processed_v2 --output results/dataset-audit-v2.json
```

The split writes `split-manifest.json` and `dataset-manifest.json` into a new output directory. The dataset manifest contains the declared version, per-split class counts, source paths, image hashes, reviewer and time, group ID, seed, and hashes of the input CSV, curation report and split manifest. Its own canonical SHA-256 detects edits. The audit checks that every output image and group agrees with both manifests and that no content hash crosses splits. Keep the curated input, review CSV, group CSV, curation report and manifests as one immutable snapshot; changing any of them requires a new version and output path. The audit checks structure and hashes, but cannot independently verify the human claim that a group represents the same physical note.

## 2. Register policy, train and decide

Copy `docs/model-quality-gates.example.json` to a new private run-specific file. Replace the dataset version, review the example thresholds against the use case, record `approved_by`, set `status=locked` and `locked_at` **before** evaluating the held-out test set. Do not edit this file after test evaluation; the report pins its exact SHA-256. Copy `docs/training-config.example.json` for the chosen seed, batch size, epoch limits and learning rates.

```bash
python scripts/run_candidate_pipeline.py --dataset-root dataset/v2/2.0.0/processed --version 2.0.0 --benchmark-image path/to/representative.jpg --training-config results/training-config-v2.json --gates-file results/quality-gates-v2.json --archive-to-s3
```

The pipeline stops before training if the dataset manifest is unverified or human review is incomplete. Each run records its ID, configuration, full epoch history, artifact hash, evaluation with per-class recall/confusion matrix/calibration, inference benchmark, quality gate decision, Git commit and platform. `scripts/record_run.py` rejects reused run IDs with changed evidence. `scripts/archive_run.py` uploads files under an immutable private S3 key and registers metadata in PostgreSQL. Repeating an identical archive is safe. If a candidate passes and an authorized reviewer decides to promote it, run `scripts/promote_release.py` with the same manifest, audit, evaluation, benchmark and locked gates file; verify the approved manifest and publish a new immutable model object. No legacy dataset or unregistered policy can pass.

**Current release-path limit:** this automated pipeline produces a Keras candidate. Render Free serves ONNX and has no TensorFlow runtime, so its release channel cannot activate that Keras run. `scripts/export_onnx.py` converts the artifact. `training/evaluate_onnx.py --release-grade --gates-file <locked-policy>` re-audits a verified grouped v2 dataset and evaluates the exact converted ONNX hash, including per-class metrics, calibration and confusion matrix; the default mode remains diagnostic. This release-grade option has passed local preflight fixture tests, but no real v2 dataset or independently evaluated ONNX candidate exists yet. Conversion, ONNX warm benchmark, quality-gate decision, approved run recording and private archival are still separate steps, not an automated end-to-end pipeline. Never promote Keras metrics as evidence for different ONNX bytes. The admin dashboard can activate only an approved compatible run; monitoring never performs automatic retraining.

Backend CI checks Python syntax, migrations, fixture audit, report schema, quality gate behavior, monitoring states and encrypted backup integrity. Heavy training and held-out evaluation run separately on a suitable training machine; their artifacts are archived and inspected before deployment.

## 3. Registry and dashboard

Alembic migration `0003_mlops_registry` adds metadata tables for runs, cloud benchmarks, monitor snapshots and API 5xx events. Private reports stay in Supabase Storage. Admin-only endpoints include `/mlops/runs`, `/mlops/runs/{run_id}`, report downloads, `/mlops/benchmarks`, `/mlops/monitoring` and `/mlops/monitoring/current`. `POST /mlops/runs/sync` backfills old archived runs into PostgreSQL. All downloaded report bytes are compared with archived hashes. The dashboard has Run list/detail, model comparison, benchmark and monitoring pages. Diagnostic results and reviewed accuracy are labeled separately from independent test-set quality.

## 4. Monitoring and alerts

`docs/free-staging-monitor-targets.json` contains provisional Render Free thresholds. `/mlops/monitoring/current` counts API 5xx events over 24 hours, p95/p99 processing and inference time, low-confidence traffic, reviewed outcomes and private bucket bytes. Drift requires an **approved model**, a verified audit/evaluation baseline and at least 100 operational predictions; reviewed accuracy is hidden below 30 reviews. Without those inputs the status is `insufficient_data`, not `healthy`. The daily GitHub Action probes the API, stores the snapshot in PostgreSQL and retains a JSON artifact. `warning` or `critical` fails the workflow for alert visibility. Scheduled GitHub Actions are best-effort, so this is a staging signal rather than paging-grade monitoring.

## 5. Backup, restore and rollback

Supabase Free does not supply automatic daily database backups. Create a **separate private backup bucket** with its own S3 endpoint and access key, plus a random 32-byte `BACKUP_KEY_BASE64`. Store all credentials in a password manager or Keychain, never in Git. The backup process needs the application source S3 settings and dedicated `BACKUP_S3_ENDPOINT_URL`, `BACKUP_S3_ACCESS_KEY_ID`, `BACKUP_S3_SECRET_ACCESS_KEY`, `BACKUP_S3_BUCKET` (optionally `BACKUP_S3_REGION`). It rejects reuse of the application's S3 access key. On a trusted client with `pg_dump` and `pg_restore`, run the following using staging DB/S3 secrets in the process environment:

```bash
APP_ENV=staging BACKUP_S3_BUCKET=<private-backup-bucket> python -m scripts.backup_staging --output-dir /private/offsite/currency-ai-backups
python -m scripts.restore_drill --backup-dir /private/offsite/currency-ai-backups/<backup-id> --confirm-isolated-target
```

For the restore command, set `RESTORE_DATABASE_URL` in the process environment from your secret manager, pointing to a newly created, empty local database; do not put its password in shell history or command arguments.

The backup encrypts the custom PostgreSQL dump, object inventory **and each private object** with AES-256-GCM before uploading to the separate bucket through its dedicated credentials. The restore drill rejects remote or nonempty database targets (including the default `postgres` database), verifies encrypted hashes and authentication tags, restores into a new local PostgreSQL database, and verifies every object copy. With `--restore-object-bucket <isolated-private-bucket>`, it also restores objects into a separate source-project bucket; it rejects the source and backup buckets as targets. Keep the encryption key and backup credentials independent of the application deploy. A complete backup needs enough private backup storage for every source object.

An isolated rehearsal on 2026-11-09 restored a PostgreSQL 16 dump and verified one object-manifest entry; [earlier evidence](evidence/2026-11-09-local-restore-drill.json). A newer full drill on 2026-11-10 restored one PostgreSQL row and two encrypted object copies into an isolated bucket; [full drill evidence](evidence/2026-11-10-local-full-restore-drill.json). Both used a local database and moto S3, **not** Supabase data. A real staging backup and restore still require a separate private backup bucket and credential setup.

After adding dedicated backup credentials and an empty-target guard, a 2026-11-11 [local end-to-end drill](evidence/2026-11-11-separate-backup-local-drill.json) ran `pg_dump` and `pg_restore`, verified one restored row and two encrypted objects, and restored both objects into an isolated bucket. The source and backup S3 clients used different test keys. This still did **not** access Supabase; a cloud backup and isolated cloud-data restore remain outstanding.

For an application rollback, retain the previous Render deploy and immutable `MODEL_S3_KEY`, restore the prior deploy and model key together, then verify `/ready`, login, prediction, history and MLOps pages. Additive migrations are forward compatible; a database restore is a separate operation. Record the actual drill, duration and any failures before claiming recovery objectives.

## 6. Acceptance and current limits

The connected-device and no-code release workflow is described in [release-control-runbook.md](release-control-runbook.md). Admins can switch only approved model runs through the dashboard; the API and online devices then poll the channel. Monitoring warnings require investigation and human approval before a new model is activated.

After each deploy, check admin/analyst authorization; prediction, review, private image viewing; run/benchmark/monitor pages; and the daily monitor. Use three images from different classes and sizes, ten warmups and 100 measured requests each at concurrency 1, 4 and 8. Save a separate cold-start measurement and a sustained-load report with commit, Render plan, model hash, error rate, throughput and p50/p95/p99. Purge benchmark traffic after preserving the reports. Do not apply paid-plan targets to Render Free.

The admin-only `DELETE /mlops/benchmark-traffic/{benchmark_run_id}` deletes records and private images only when the matching benchmark report is already in the registry. Repeating cleanup is safe and does not delete the retained report.

The current human review queue is incomplete, so model 1.1.0 remains `candidate` and production startup must continue to reject it. Any backup/restore and rollback evidence must describe what was actually exercised on cloud versus an isolated local drill.
