# Free staging: deploy and evidence

This is a **demonstration staging environment**, not a production SLA. The current model is a `candidate`; its historical test split contains cross-split duplicates and has no verified physical-note group IDs. Do not claim release accuracy from it.

## Architecture and limits

- Render Free web service (`render.free.yaml`): 0.1 CPU, 512 MB RAM. It sleeps after 15 minutes idle and wakes on request; cold start can take about a minute. Its disk is ephemeral. The ONNX Runtime variant avoids importing TensorFlow into the serving process.
- Render free static site (`currency-frontend/render.free.yaml`): React dashboard, history review, user administration and MLOps run summaries.
- Supabase Free: an isolated PostgreSQL project (500 MB database) and private S3-compatible Storage bucket (1 GB). Free projects pause after inactivity. Keep staging records and model artifacts within quota; choose a paid plan for a public production service.

The backend migration runs at container startup because Render Free has no pre-deploy command. Only one web instance is configured. Database migrations must remain backward compatible with the previous deploy. Preserve a database export before changing schema.

## 1. Verify and publish the runtime artifact

The ONNX variant is derived from the pinned Keras candidate. Its manifest remains `candidate`, with `dataset_version=legacy-unversioned` and no certified test metrics.
Both training evaluation and API serving now use nearest-neighbor resize, recorded in the manifest. This removes a preprocessing mismatch found when comparing the old Keras evaluation with the API's former PIL default resize. The same-input Keras/ONNX comparison must be retained with the evaluation evidence.

```bash
python -m scripts.export_onnx
python scripts/verify_release.py --manifest models/edge-manifest.json --model models/efficientnetb0_candidate.onnx --require-artifact
python -m training.evaluate_onnx
```

The diagnostic evaluation report is `results/onnx-evaluation.json`. It records artifact hashes, class metrics, ECE, latency and the host. It is ignored by Git; copy it into a private run archive. The source Keras artifact stays unchanged.

Create a **private** Supabase Storage bucket. In Storage settings enable S3 protocol and generate server-side S3 keys. Put them only in Render secrets or a local secret environment. Set `S3_ENDPOINT_URL` to the project-specific `https://<project-ref>.storage.supabase.co/storage/v1/s3` endpoint and use its region. The backend forces path-style S3 addressing. Use a separate staging Supabase project and bucket from production.

```bash
export S3_BUCKET=<private-bucket>
export MODEL_S3_BUCKET="$S3_BUCKET"
export MODEL_S3_KEY=staging/models/1.1.0/efficientnetb0_candidate.onnx
python -m scripts.publish_artifact --manifest models/edge-manifest.json --model models/efficientnetb0_candidate.onnx --target staging
```

The object key is immutable. If the export bytes change, create a new key and update the Render environment; never overwrite an existing artifact.

## 2. Provision free services

1. Create a Supabase Free project and obtain its PostgreSQL connection string. Use `sslmode=require`, and keep the password secret. Create a private Storage bucket and S3 keys as above.
2. Push the reviewed backend and frontend changes to Git. Connect each repository in Render. Use `render.free.yaml` as the backend Blueprint path and `render.free.yaml` in the frontend repository for the static site.
3. Set backend Blueprint prompts: `DATABASE_URL`, exact frontend origin in `CORS_ORIGINS`, a strong `ADMIN_PASSWORD`, `ADMIN_USERNAME`, `S3_BUCKET`, `S3_REGION`, `S3_ENDPOINT_URL`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`. `SECRET_KEY` is generated by Render.
4. Set frontend `VITE_API_URL` to the backend HTTPS URL, then deploy the static site. Set backend `CORS_ORIGINS` to the actual static-site HTTPS origin and redeploy if its generated name differs.
5. Verify `/ready`, admin login, `/model-info`, `/stats`, `/mlops/runs`, prediction, history image signed URL, review and deletion. An unauthenticated staging prediction must return 401.

Do not put S3 credentials or admin password in `VITE_*` values or Git. The dashboard's MLOps section lists the last 20 archived run summaries for admins only. If no run has been archived, the empty state is expected.

## 3. Measure and retain results

Use at least three JPEGs from different classes and sizes. Save the actual Render plan, region, deploy commit, model hash, client machine and warm/cold state alongside each result. Use a staging analyst account. Benchmark traffic is tagged, excluded from dashboard statistics, and can be purged after reports are retained.

```bash
python scripts/benchmark_api.py a.jpg b.jpg c.jpg --url https://<backend>.onrender.com --token-env STAGING_TOKEN --runs 100 --warmups 10 --concurrency 1 --output results/free-staging-c1.json
python scripts/benchmark_api.py a.jpg b.jpg c.jpg --url https://<backend>.onrender.com --token-env STAGING_TOKEN --runs 100 --warmups 10 --concurrency 4 --output results/free-staging-c4.json
python scripts/benchmark_api.py a.jpg b.jpg c.jpg --url https://<backend>.onrender.com --token-env STAGING_TOKEN --runs 100 --warmups 10 --concurrency 8 --output results/free-staging-c8.json
```

These three profiles and a separate cold-start request are required before writing any cloud latency target. The existing `docs/staging-targets.json` applies to the **paid 1 CPU / 2 GB** profile and must not be used to judge the Free tier. Purge each benchmark run after saving its JSON report: `APP_ENV=staging python -m scripts.purge_benchmark --run-id <benchmark_run_id> --execute` with staging DB/S3 credentials.

For periodic operations monitoring, set GitHub Actions repository variable `STAGING_URL` and secrets `STAGING_USERNAME`, `STAGING_PASSWORD`. `.github/workflows/staging-monitor.yml` probes readiness, login, statistics, model metadata and archived runs daily, retaining JSON artifacts for 30 days. Failed probes fail the workflow. Separately run `scripts/drift_report.py` against the staging DB with a valid held-out baseline; its class-mix and low-confidence signals are diagnostic and require review.

## 4. MLOps record and rollback

The candidate pipeline writes a run folder containing the audit, training history, held-out evaluation, benchmark, manifest, hashes, Git commit and environment. After a successful verified run, archive it in the private bucket with `python -m scripts.archive_run results/runs/<run-id> --target staging`, or add `--archive-to-s3` to `run_candidate_pipeline.py`. Do not archive a run as `approved` unless the grouped data and release gates pass.

Render Free supports rollback to the two recent deploys, but rollback does not reverse database migrations or overwrite immutable model objects. Switch to the prior deploy and prior `MODEL_S3_KEY`, then verify `/ready`, model version, prediction and history. Preserve database exports and the previous model artifact.

## Remaining release blocker

Review the two conflicting-label groups, fill `group_id` from physical note or capture-session evidence, create a grouped split, audit it, retrain and evaluate. Until then, the candidate is usable only as a diagnostic staging demo. The production startup gate continues to reject it.
